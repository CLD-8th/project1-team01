# 필수 질문 답변 (펩시미만잡)

> 09-28 교안 10번 "필수 질문 및 답변 작성"이 요구하는 공식 5문항. 노션 페이지엔 팀이 자체적으로 만든 7문항(용량·NAT·Redis·병목 관련)이 이미 있는데, 이건 그것과 별개로 **배점 20%짜리 공식 문항**이라 빠지면 안 됨.

## 공식 필수 질문 5개

| 질문 | 답변 |
|---|---|
| 한 AZ 전체가 중단되면 서비스는 어떻게 되는가 | ALB가 헬스체크 실패를 감지해 트래픽을 살아있는 AZ로만 라우팅. RDS는 Multi-AZ 자동 장애조치(수십 초 전환). 죽은 AZ에 NAT가 있었다면 반대편 App 서브넷 아웃바운드만 일시 불가하고, 사용자 트래픽 자체는 정상 처리됨 |
| RDS Primary 장애 시 애플리케이션은 어떻게 새 Primary에 접속하는가 | Multi-AZ 자동 장애조치 시 엔드포인트(도메인)는 동일하게 유지되고 DNS가 내부적으로 새 Primary(기존 Standby)를 가리키도록 전환됨. 전환 중 수십 초 순단은 애플리케이션의 커넥션 재시도 로직으로 흡수, 코드·설정 변경 불필요 |
| 트래픽이 예상의 5배가 되면 설계의 어느 부분이 먼저 한계에 도달하는가 | 급증 RPS 7.2×5=36. 앱 계층은 최대 3대(60RPS)로 아직 버티지만 여유가 줄어듦. 그보다 먼저 **DB 커넥션**이 병목일 가능성이 큼(읽기:쓰기 8:2, 읽기 전용 복제본 없음) — 이 시점에 RDS Proxy나 읽기 전용 복제본 도입을 검토하게 됨 |
| 비용을 절반으로 줄여야 한다면 무엇을 포기하고, 어떤 위험을 받아들이는가 | RDS Multi-AZ→Single-AZ로 전환(월 $127→약 $64, 비용의 절반 이상 절감). 위험: RDS 장애 시 자동 장애조치가 사라져 수동 복구로 전환되고, RTO가 30분을 훨씬 넘어 수 시간 단위로 늘어날 수 있음 |
| 개발자가 운영 DB에 직접 접속해야 하는 상황이면 어떻게 접속하는가 | DB는 프라이빗(Data) 서브넷에 있고 db-sg 인바운드 소스가 app-sg뿐이라 외부에서 직접 접근 불가. **SSM Session Manager**로 App 서브넷의 EC2에 먼저 접속(22번 포트 개방 없이 IAM 권한 인증, 접속 기록은 CloudTrail에 남음)한 뒤, 그 EC2를 경유해 DB 접속 |

## 팀 자체 질문 7개 (최종본, 노션과 동일)

| 질문 | 답변 |
|---|---|
| 1대가 몇 RPS를 처리하는지 모르면 설계가 되는가 | 대상 추적 정책은 그 값을 필요로 하지 않음. 저희가 정한 것은 목표 지표(CPU 60%)와 최소·최대이고 최소는 가용성에서, 최대는 급증 가정과 비용에서 나왔음. 20 RPS는 타당성 확인용 가정이며 k6로 실측해 보정할 예정 |
| 최대를 3대로 정한 근거가 무엇인가 | 급증 3배를 그대로 적용하면 2×3=6대지만 비용 부담으로 3대로 조정함. 급증 7.2 RPS는 2대(40 RPS 가정)로도 감당되어 3번째는 가정 오차와 AZ 장애 중 급증이 겹치는 경우를 위한 여유임 |
| 트래픽이 최대 3대로도 부족하면 어떻게 하는가 | 정의서의 급증 가정을 넘어서는 구간이므로 응답 지연을 감수함. 상시로 부족해지면 급증 가정을 재검토한 뒤 최대 대수를 늘림 |
| 왜 CPU 60%인가 | AZ 한 곳이 죽으면 남은 1대가 전체 트래픽을 받아도 급증 시 CPU 약 36%로 60% 아래라 과부하가 없음. 그 이상으로 커지면 Auto Scaling이 대체·추가 인스턴스를 기동함(워밍업 300초, RTO 30분 안) |
| NAT Gateway를 1개만 둔 이유는 무엇인가 | 사용자 요청 경로가 아니라 서비스 서빙 영향이 낮고 월 고정 비용을 약 50% 줄임. 해당 AZ 장애 시 새 인스턴스 기동이 막히는 위험은 인지하고 있고 트래픽이 커지면 AZ별 2개로 전환함 |
| Redis가 죽으면 어떻게 되는가 | 랭킹은 RDS 거래 요청 데이터로 재집계할 수 있고 락은 TTL이 수 초라 영향이 작음. 일시적으로 RDS 부하가 늘 수 있어 DB 상태 검증으로 중복 수락을 막음 |
| 확장의 다음 병목은 어디인가 | DB 커넥션이라고 봄. 읽기:쓰기가 8:2라 그 시점에는 읽기 전용 복제본이나 RDS Proxy를 검토하게 됨 |

(Q3 "트래픽이 최대 3대로도 부족하면"의 이전 버전엔 "Redis 캐시 적중률 개선"이라는, 우리 시스템과 안 맞는 문구가 있었으나 팀이 수정 반영함 — Redis는 랭킹·락 용도로만 쓰여 "적중률" 개념 자체가 없음.)

## 추가 예상 질문 4개 (겹치지 않는 영역)

| 질문 | 답변 |
|---|---|
| Multi-AZ를 적용했으니 읽기 성능도 좋아지나? | 아니오. Multi-AZ의 Standby는 동기 복제 대기용이라 읽기 트래픽을 분산 못 함(09-22 교안이 짚은 흔한 오해). 읽기 성능 분산이 필요하면 별도 읽기 전용 복제본을 둬야 함 — 지금은 트래픽이 작아 안 둠 |
| 도서 목록/상세 조회에는 왜 캐시를 안 뒀나? | Redis는 랭킹·락 용도로만 씀. 피크 RPS가 2.4~7.2로 작아 DB 직접 조회로 충분하다고 판단. 트래픽 늘어 DB가 병목되면 그때 조회 캐시 도입 검토 |
| t4g(ARM/Graviton) 인스턴스를 고른 이유는? | 동일 성능 대비 x86(t3) 대비 약 20% 저렴. Docker 이미지가 멀티플랫폼 빌드라 ARM 종속성 문제 없음(eclipse-temurin 공식 이미지 arm64 지원) |
| 락 TTL 5초 안에 처리가 안 끝나면? | 락이 자동 만료돼 다른 요청이 처리 가능해짐. 데이터 정합성은 최종적으로 DB 상태로 검증 — 락은 속도 최적화용이지 유일한 안전장치는 아님 |

## 설계 보완 — 예약 조정(Scheduled Scaling) 누락

도메인정의서의 급증 이벤트("시험 시즌·학기 초 모집 집중")는 **시점이 예측 가능한** 이벤트인데, 지금 Auto Scaling 정책은 대상 추적(Target Tracking)만 있고 예약 조정이 없음. 09-22 교안이 정확히 이 케이스를 "자주 누락되는 것"으로 짚었음 — "피크 시각이 확정적인데 지표 반응을 기다릴 이유가 없다".

**반영**: `05_용량산정.md`의 스케일링 정책에 예약 조정을 대상 추적과 병행하는 것으로 추가함(아래 참고).
