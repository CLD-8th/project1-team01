# 회고 (펩시미만잡)

> 문제 → 원인 → 해결 → 배운 점 순서로, 프로젝트 마무리 시점에 작성.

## 문제

- 구현에 시간이 너무 많이 들어서 설계·문서 작업 시간이 빠듯했다.
- 작은 규모 서비스(DAU 2,400)인데 EC2 Auto Scaling·RDS Multi-AZ 적용으로 비용(월 $215.95)이 체감상 과해 보였다.
- 용량 산정·비용 산정 과정에서 숫자가 여러 번 바뀌면서, 문서 간 숫자가 서로 안 맞는 사고가 반복됐다(인스턴스 1대 처리량 2 RPS→20 RPS→30 RPS 왔다갔다, Auto Scaling 최소 용량이 실수로 2→1로 바뀜, 동일 항목 비용이 문서마다 $12/$25로 다르게 적힘).
- 교안/문서가 여러 곳(Notion, 로컬 docs, 팀원 각자 메모)에 흩어져 있어 최신 상태가 뭔지 헷갈리는 순간이 많았다.

## 원인

- 화면 디자인·세부 기능에 공수를 들이다 보니 "최소 기능 동작"이라는 우선순위가 뒤로 밀렸다.
- Auto Scaling 최소 2대의 근거가 "트래픽 처리량"이 아니라 "AZ 이중화(가용성)"라는 걸 체감하기 전까지는, 작은 트래픽에 큰 인프라를 쓰는 게 불합리하게 느껴졌다 — 가용성 요구사항 자체가 비용을 결정한다는 인과관계를 뒤늦게 명확히 했다.
- 가정값(인스턴스 처리량, 비용 추정치)을 근거 없이 빠르게 고쳐나가는 과정에서, 바뀐 값을 참조하는 다른 섹션(ADR·용량산정표·비용산정표)까지 같이 고치지 않고 넘어간 경우가 있었다.
- 여러 명이 동시에 같은 Notion 페이지를 편집하면서, 한쪽에서 고친 값이 다른 쪽 근거 텍스트에는 반영 안 되는 일이 반복됐다.

## 해결

- 강사님 지시대로 화면 완성도를 포기하고 "핵심 기능 동작"을 최우선 기준으로 재조정, 백엔드 API 11개를 데드라인 안에 전부 merge했다.
- 비용 문제는 "요구사항(RTO 30분·RPO 5분·가용성 99.9%)이 있는 한 Multi-AZ 비용은 그 요구사항의 가격표"라는 논리로 정리하고, 발표자료에 "설계 전제" 섹션을 따로 만들어 Single-AZ로도 트래픽은 충분하다는 점과 그럼에도 Multi-AZ를 선택한 이유를 먼저 밝혀뒀다. 대신 NAT Gateway 단일화·ElastiCache 단일 노드로 줄일 수 있는 비용은 최대한 줄였다.
- 숫자 불일치는 발견할 때마다 관련된 모든 섹션(용량산정·ADR·비용산정)을 한 번에 같이 고치는 방식으로 대응했고, 제출 직전에 전체를 한 번 더 통독하며 교차 검증했다.
- 로컬 docs와 Notion 두 군데에 흩어진 걸 최종적으로 한 번에 동기화하고 git에 커밋해 "진실의 원천"을 하나로 모았다.

## 배운 점

- 용량 산정에서 중요한 건 숫자의 정확도가 아니라 "가정을 몇 개로 줄였는지"와 "그 가정을 왜 그렇게 잡았는지"다 — 우리는 4개 가정(피크집중률·체류시간·Think Time·급증배수)만 정하고 나머지는 전부 계산으로 끌어내는 방식으로 질문받을 지점을 최소화했다.
- 비용이 커 보이는 건 설계가 잘못됐다는 신호가 아니라, 어떤 요구사항이 비용을 지배하는지 보여주는 신호였다 — 우리 경우 RDS Multi-AZ 하나가 전체 비용의 59%를 차지한다는 걸 알고 나니, "비용을 절반으로 줄이면 뭘 포기하는가"라는 질문에도 바로 답할 수 있었다.
- AWS 공식 권장사항(AZ마다 NAT Gateway 1개 등)과 다르게 설계해도 괜찮다 — 중요한 건 권장사항을 몰라서 놓친 게 아니라, 알고도 트레이드오프를 따져서 의도적으로 선택했다는 걸 문서로 남기는 것이다.
- 여러 사람이 같은 설계 문서를 계속 고치는 프로젝트에서는, 값 하나를 바꿀 때마다 그 값을 참조하는 다른 모든 곳을 같이 확인하는 습관이 없으면 금방 앞뒤가 안 맞는 문서가 된다 — 다음 프로젝트에서는 숫자가 나오는 곳을 한 곳(예: 용량산정표)으로 모으고 나머지는 거기를 참조만 하는 구조를 더 일찍 잡아야겠다.
